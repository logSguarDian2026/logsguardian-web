About

A thesis, built to be installed

logSguarDian is a graduation thesis at Universidad del Valle de Guatemala (2026). It was built as an npm package that a small team could run in front of production traffic, and it was evaluated against criteria that it does not fully meet.

Sebastián Huertas Gómez

Implemented the initial 72-feature extractor and its move to worker_threads. Also built the cybersecurity component and the npm package side of the library.

Diego Pablo Valenzuela Palacios

Analyzed and justified each feature, defined which features do not exist at inference time, and fixed the input contract. Added four features and their corrections, and built the training, ONNX export, and retraining pipeline. Built the machine learning component.

Thesis advisor: Ing. Erick Francisco Marroquín Rodríguez. Catedrático: Ing. Bacilio Alexander Bolaños Lima. The original idea of a library that combines artificial intelligence and cybersecurity came from Ing. Wilson Iván Félix Reyna.

Status

Where the package stands

Published: logsguardian@ was published on npm on 11 October 2026. Version 0.1.0 was published on 30 August 2026. Version contains the rf_v11 / if_v10 models whose metrics are reported in the thesis.

Tests pass in the repository: 68 extractor tests, 147 core middleware tests, and 113 CLI tests, as recorded in the repository status report of 16 August 2026. Some middleware tests depend on real timer margins and can fail under heavy parallel load.

Exploratory work

An MLOps pipeline, outside the evaluated objectives

Built as separate infrastructure, not as part of the npm package or its runtime dependencies. The thesis presents it as a recommendation for teams that adopt logSguarDian at scale.

  1. Telemetry collection: receives only the 76-feature vector of each classified request, never the raw payload.
  2. Fleet simulation: several simulated sources send telemetry concurrently.
  3. Anomaly clustering: Isolation Forest and DBSCAN run on the 63 features that the unsupervised model uses.
  4. Human curation: a command-line interface reviews the resulting clusters.
  5. Orchestrated retraining: unifies the curated corpus, retrains the hybrid model, and generates the ONNX artifacts.
  6. Validation: five acceptance gates, checked in order and stopped at the first failure.
  7. Canary deployment: a replay of the labeled test corpus, plus a bounded shadow window on live traffic.
  8. Promotion or rollback: promotion requires zero attacks let through that production blocks, and at least 99.5% agreement on blocking decisions.

As a proof of concept, the retraining pipeline ran on 29 August 2026 with simulated telemetry: 244 events from five simulated sources and one dedicated source. It is not a production service.

Contributing

The most useful feedback is a case where the library gets it wrong

This is a research project with stated limitations, not a finished commercial product. If you run WAFs or RASP tools in production, or want to test the methodology, that feedback helps most. Read the known limitations before reporting a duplicate.
