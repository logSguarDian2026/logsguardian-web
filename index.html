RASP middleware · Node.js / Express

Your Express app, inspecting its own traffic.

logSguarDian is a one-line middleware. A Random Forest trained on 268,240 labeled HTTP requests decides when to block SQL injection, XSS, path traversal, and command injection, before your route handlers run. An Isolation Forest logs anomalies but never blocks.

Why

Most small teams can't staff a security team, or tune a WAF.

Small and mid-sized Node.js teams often run without a dedicated security function. A properly tuned WAF like ModSecurity is powerful, but writing rules, managing paranoia levels, and chasing false positives takes expertise most small engineering teams don't have.

Install, don't operate

One middleware line after your body parsers. No reverse proxy to stand up and no separate service to keep alive. The middleware runs in your process.

Statistical, not signature-based

A Random Forest classifies request structure instead of matching known strings. On the held-out test set it separates the classes well, and the test set is not a substitute for real traffic (see Limitations).

Designed to sit behind a WAF

It is meant for defense in depth, not as a replacement. In our layered test it caught 37 of the 40 attacks that ModSecurity let through. See the measurement →

How it works

A hybrid model, running off the event loop.

Every request becomes a 76-feature vector. Two ONNX models score it in dedicated worker threads, so inference does not block Node's event loop.

Random Forest — the blocking authority

Uses 69 of the 76 features and classifies each request as benign, sqli, xss, path_traversal, or cmdi. If the top class is an attack and its confidence reaches the threshold (0.35 by default), the request gets an HTTP 403. RF is the only model with blocking authority.

Isolation Forest — anomaly logging, never blocking

Uses 63 features, trained only on benign traffic. It flags requests that look statistically unusual, for logging and webhooks. A pass_anomaly verdict never becomes a 403.

Fail-open, by design

If the RF worker has not loaded, has crashed, or does not answer within timeoutMs (50 ms by default), the request is forwarded unchanged.

What does not meet its criteria

Memory and CPU are over budget. Latency meets its absolute limit only under normal and attack load.

Criteria come from the thesis's approved protocol. Measurements come from a Docker and Postgres run on a 2-vCPU Linux runner, using an earlier build of the model than the one in version 0.1.1 (see the note in Evaluation).

Memory not met

Added memory is +331.9 MiB under attack and +332.0 MiB under normal load, against a 150 MB (≈143 MiB) criterion. Under volume load it is +375.9 MiB.

CPU not met

Relative CPU increase is +529.6% under attack and +614.4% under normal load, against a criterion of up to 15%.

Latency, normal and attack load met

Absolute p95 overhead is 12.08 ms under normal load and 12.85 ms under attack load, against a 15 ms limit.

Latency, volume load not met

Overhead rises to 6,495.46 ms at p95, and 7.00% of requests time out in that scenario.

Said plainly

Where it is still limited.

Three limits matter most before you install. The full list is on the Limitations page.

Browser User-Agents can trigger false positives

The User-Agent is one of the strongest features. With a browser User-Agent, the model blocked 97.1% of benign requests in OWASP Juice Shop (monitor mode) and 92.5% in dvws-node (block mode).

No online learning

Models are trained offline and shipped fixed with each release. Detection quality depends on the version you install, not on how long it has run against your traffic.

pass_anomaly is a log signal, not a block

The Isolation Forest never blocks, and it flags 19 of the 39 attacks that Random Forest lets through on validation, at the cost of 866 benign requests. Treat it as a noisy log signal.
